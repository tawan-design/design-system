Figma file structure (what Claude expects)

📁 Design System (Figma file)
 ├─ 📄 Foundations   ← variable collections live here
 │    ├─ Collection "Primitives"  (color/blue/600, space/16, radius/8 …)
 │    └─ Collection "Semantic"    modes: Light, Dark  (bg/surface, text/muted …) → aliases to Primitives
 ├─ 📄 Components    ← one component set per component, variant properties named like props
 │    └─ Button  (Variant = Primary|Secondary|Ghost|Danger, Size = Small|Medium|Large, State = Default|Disabled)
 └─ 📄 Patterns      ← proven compositions (review dialog, empty state …)

Naming rules that make the agent accurate:

  • Variable names use /: bg/surface, space/16. They become color.bg.surface → --ds-color-bg-surface → bg-surface.
  • Component property names match code props: Variant → variant, Size → size.
  • Every fill, stroke, gap, padding and radius is bound to a variable. No detached values.
Chapter 3

Tokens

Creating and changing foundations.

Recipe A

Create the foundations (first time)

Goal
Brand direction → working tokens in Figma and code, light + dark
Who
DS owner (+ brand/marketing input)
Where
Cowork (Figma side) → Claude Code (repo side)
Attach / provide
Brand guidelines or moodboard (PDF/images) · existing product screenshots · Figma DS file URL
Skills
🧩 figma-use + figma-generate-library (create variables in Figma) · ✅ ds-tokens-sync (Figma → repo) · 🧩 design:accessibility-review (contrast)
Connectors
Figma · GitHub

Steps

  1. Decide the scales with Claude: color ramps, spacing (2–64), radius (8, 12, full), type sizes.
  2. Create variables in Figma. Claude writes the Primitives and Semantic (Light/Dark) collections into your file.
  3. Check contrast for every text/background pair in both modes.
  4. Sync to the repo. Claude exports the variables to tokens/*.json, rebuilds, and opens a PR.
  5. Review Storybook → Foundations (toggle Dark). Merge.

Sample prompts

Step 1–2 (Cowork):

I'm setting up foundations for our design system. Attached: brand guidelines + 3 product screenshots.
Figma file: <URL>

1. Propose primitives: color ramps (neutral, brand, red, green, 50–950), spacing 2–64,
   radius 8/12/full, type sizes 12–32.
2. Propose semantic tokens with names like bg/surface, bg/brand, text/default, text/muted,
   border/default, border/focus, for Light and Dark.
3. Show me a table first. After I approve, create them as Figma Variables on the
   "Foundations" page: collection "Primitives", and collection "Semantic" with modes Light/Dark
   aliasing primitives. Use figma-use and figma-generate-library.

Step 3:

Run an accessibility review on every text/* on bg/* pair in both modes. Flag anything below
WCAG AA (4.5:1 body, 3:1 large text/UI) and suggest the closest passing primitive.

Step 4 (Claude Code, in the repo):

Use ds-tokens-sync. Figma file: <URL>. Replace the sample tokens with ours, update the @theme
block in packages/ui/src/styles.css for any new semantic tokens, run pnpm check, add a changeset,
and open a PR labelled "tokens".

Output: tokens/*.json, updated styles.css, Foundations page in Storybook, tokens PR Done when: ☐ both modes pass AA ☐ no raw values in Figma components ☐ Storybook Foundations matches Figma ☐ PR merged

Recipe B

Change, add or rename a token

Goal
Update tokens safely, without silently breaking products
Who
DS owner (anyone can request via the "Token change" issue)
Where
Figma → Claude Code
Attach / provide
The issue link · Figma file URL · what changed
Skills
✅ ds-tokens-sync

Figma · GitHub

Steps

  1. Edit the variable in Figma.
  2. Claude syncs and classifies each change: added / value changed / renamed-removed (= breaking).

Chapter 4

Components

Building, extending and syncing components between Figma and code.

Recipe C

Create a new component

Goal
A pattern proven in real screens → a DS component in Figma and code, 1:1
Who
DS owner (designer builds in Figma, Claude builds code) · 1 engineer reviews
Where
Figma → Claude Code
Attach / provide
Figma URL of the component set (right-click → Copy link to selection) · the GitHub issue · 1–2 real screens where it's used · any behavior notes (keyboard, empty/loading/error)
Skills
✅ ds-component-from-figma · 🧩 figma-code-connect · 🧩 design:accessibility-review
Connectors
Figma · GitHub

Before you start (in Figma)

  • ☐ Component set exists with variant properties named like props (Variant, Size, State)
  • ☐ All states drawn: default, hover, focus, disabled, error, loading (where relevant)
  • ☐ Every value bound to a variable (run design:design-system to audit it if unsure)
  • ☐ Used in ≥2 real screens (otherwise it stays a local pattern)

Steps

  1. Claude checks catalog.json. If something similar exists, it proposes a variant instead (→ Recipe D).
  2. Claude reads the Figma node: properties → props, variables → token classes. It stops and reports any unbound value instead of guessing.
  3. Builds <Name>.tsx (cva variants, Radix if interactive), <Name>.stories.tsx (every variant and state + Figma link), <Name>.figma.tsx (Code Connect).
  4. Exports it, regenerates catalog.json, runs pnpm check, adds a minor changeset, opens a PR.
  5. → Recipe E (review).

Sample prompt (Claude Code, in the repo)

Use ds-component-from-figma to create a <Select> component.
Figma component set: <URL>
Issue: #<n>
Used in: <URL of screen 1>, <URL of screen 2>

Behavior notes:
- Built on Radix Select, keyboard navigable, typeahead
- Props: label, hint, error, placeholder, options, disabled
- States in Figma: Default, Open, Focus, Error, Disabled

Map Figma properties 1:1 to props. If any fill/spacing/radius isn't bound to a variable,
stop and list them, don't guess. Write stories for every variant and state with the Figma link,
add Code Connect, regenerate the catalog, run pnpm check, add a minor changeset and open a PR
using the template.

Output: component + story + Code Connect + catalog entry + PR with preview link Done when: ☐ every Figma variant has a story ☐ pnpm check green ☐ a11y panel has no violations ☐ Code Connect published (npx figma connect publish)

Chapter 5

Build the system

How we turn the Figma library into code, and wireframes into real screens. Figma is the only source of truth.

Build roadmap

We don't convert every Figma component up front. Reviewing 30+ components at once is shallow, unused code rots, and a mistake in the first conventions would repeat everywhere. Instead: tokens, then a small core wave, then build on demand as real screens need components.

PhaseWhatDone when
0 · TokensFigma variables → code (A). Light/Dark with Brand 1, Balanced radius, Font1 as defaults. Figma names kept as-is (content-primary, surface-canvas, action-brand…). Repo skills updated to the new names.Storybook Foundations shows the real palette, type, spacing and radius
1 · Clean slate + core waveRemove the starter sample components. Build the 8 most-used components from Figma, 1–2 per PR (C): Button, Icon, Icon Button, Text-Field, Badge, Checkbox, Toggle, ModalEach approved in Chromatic and listed in catalog.json
2 · Screen-drivenEach wireframe pulls in the components it needs (L). Components missing from Figma go through Labs (M)Ongoing
3 · ThemesBrand 2, Sharp/Rounded radius, Font2 as switchable themesAll modes switchable in Storybook
4 · PlaygroundRebuild the sample product screens from the crypto componentsPlayground uses only the official library

Rules of the build

  1. Figma decides, code follows. Component names and properties match Figma (Type, Tone, Size → type, tone, size).
  2. One component (or 2 closely related) per PR, reviewed visually in Chromatic.
  3. Labs is never official. Labs components aren't in catalog.json, so agents can't use them in products.
  4. Promote only from Figma. A Labs component becomes official only after its Figma version is refined and moved to its own page.
  5. Check IA before visuals. First confirm the screen has the right content, data and actions; then judge how it looks.
Recipe L

Wireframe → real screen (with IA check)

Goal
A wireframe becomes a real screen built only from the design system, with the same information architecture
Who
Designer (confirms IA, reviews visuals) · Claude (inventory, build, IA check)
Where
Claude Code → apps/playground → PR → Chromatic
Attach / provide
Wireframe screenshot(s) · who the screen is for and its main task · real or sample data notes · breakpoints
Skills
🆕 ds-wireframe-to-screen (planned) · ✅ ds-build-screen · ✅ ds-audit · 🆕 ds-labs (planned, for gaps)
Connectors
GitHub · Figma (only when a gap needs a Labs draft)

Steps

  1. You send the wireframe.
  2. IA inventory (no code yet). Claude lists every region, content item, data field, action and state it sees, top to bottom.
  3. You confirm the inventory. Fix anything misread. This list becomes the contract for the screen.
  4. Component map. Each inventory item → an official component from catalog.json, or a GAP.
  5. Build the screen in the playground. Gaps go to Labs (Recipe M), never hand-rolled.
  6. IA check. Claude compares the built screen with the confirmed inventory and reports ✔/✖ per item: missing, extra, wrong order, wrong data or wrong action.
  7. Visual review. You judge how well it adapts in the Chromatic preview. Claude also runs ds-audit to check that the screen really used the system.

Sample prompt (Claude Code)

Use ds-wireframe-to-screen. Wireframe attached: "Portfolio overview".
User: retail crypto investor checking holdings. Breakpoints: 375 / 1280.
Step 1 only: give me the IA inventory as a table (region · item · data · action · state).
Don't build until I confirm it.

IA check report, example

#Inventory itemBuilt asResult
1Header · total balance + 24h changeHeading + Badge tone="success"✔
2Holdings list · coin, amount, value, changeList Item × n✔
3"Buy" primary actionButton type="filled" tone="brand"✔
4Allocation chartLabs: DonutChart⚠ GAP → Labs
5Empty state when no holdings–✖ missing

Output: confirmed IA inventory · screen PR · IA check table · ds-audit score Done when: ☐ inventory confirmed by the designer ☐ IA check all ✔ (or gaps logged) ☐ visuals approved in Chromatic ☐ audit ≥ 85

Recipe M

Labs: draft a missing component, then promote it

Goal
A screen needs something the library doesn't have. Draft it safely, try it in real screens, then make it official from Figma.
Who
Claude (drafts) · Designer (refines in Figma, decides on promotion) · DS team (approves)
Where
Code: packages/ui/src/labs/, imported from @tawan-design/ui/labs, shown under "Labs" in Storybook · Figma: the 🧪 LABS page of the DS file
Attach / provide
The GAP from Recipe L · the screen(s) that need it · any reference you like
Skills
🆕 ds-labs (planned) · 🧩 figma-use + figma-generate-library (Figma draft) · ✅ ds-component-from-figma (promotion)
Connectors
Figma · GitHub

Steps

  1. Draft in code. Claude builds it in labs/ with token classes only, plus a story under "Labs/". It is not added to catalog.json.
  2. Draft in Figma. Claude creates a matching draft on the 🧪 LABS page, bound to your variables.
  3. Use it in the playground screen that needed it.
  4. Refine in Figma. The designer polishes the draft: variants, states, naming.
  5. Promote once it's used in ≥2 real screens (GOVERNANCE.md). Move the Figma component from LABS to its own page, then Claude rebuilds it from Figma into the official library (Recipe C) and deletes the Labs version.

Sample prompt (Claude Code)

Use ds-labs for the GAP "DonutChart" from the Portfolio screen.
Draft it in packages/ui/src/labs with a Labs story, and a matching draft
on the 🧪 LABS page in Figma: <Figma file URL>. Use only existing variables.
Show me both before using it in the screen.

Output: Labs component (code + Figma draft) → later an official component PR Done when: ☐ draft exists in both places ☐ never listed in catalog.json while in Labs ☐ promoted from the refined Figma version, Labs copy removed

Chapter 6

Review & QA

Approving changes and measuring how closely the UI matches Figma.

Recipe E

Design review of a component PR (the first review)

Goal
Approve or request changes before anything reaches products
Who
Designers (visual) · Engineer (code/API) · DS owner (final approval)
Where
GitHub PR → Chromatic / Storybook preview link → Cowork for an AI review
Attach / provide
PR link · Storybook preview link · Figma URL
Skills
🧩 design:design-critique · 🧩 design:accessibility-review · ✅ ds-design-qa (Recipe F)
Connectors
GitHub · Figma

Steps

  1. Designers open the preview link in the PR. For each story: compare with the embedded Figma frame, play with Controls, switch Theme to Dark, tab through with the keyboard.
  2. Claude produces a critique + accessibility report (prompt below). Paste it as a PR comment.
  3. Engineer reviews prop naming, composition and Radix usage.
  4. DS owner approves in Chromatic + GitHub, then squash-merges.

Sample prompt (Cowork)

Review PR <link>. Storybook preview: <link>. Figma: <URL>.
1. design-critique: hierarchy, consistency with our other components, states coverage.
2. accessibility-review: contrast in both themes, focus visibility, keyboard, ARIA, target size ≥40px.
3. Compare the props in the PR against the Figma component properties: list anything missing or renamed.
Give me a short comment I can paste into the PR: ✅ approve / 🔁 request changes, with a numbered list.

Review checklist (paste into PR)

  • ☐ Matches Figma in every variant/state (light + dark)
  • ☐ Prop names = Figma property names
  • ☐ Keyboard + focus ring work, screen reader label makes sense
  • ☐ Only token classes (pnpm check green)
  • ☐ Story exists for each state
Recipe F

Design QA: how well does the UI match Figma?

Goal
A measurable match score between Figma and the built UI (component or full screen)
Who
Designer (owner of the screen) · Claude does the comparison
Where
Claude Code (needs Playwright to screenshot) or Cowork with the repo connected
Attach / provide
Figma frame URL · Storybook story URL or playground/product URL (+ viewport size)
Skills
✅ ds-design-qa (+ script pnpm qa:snapshot) · 🧩 figma-design-to-code (reads design context)
Connectors
Figma

What gets compared | Check | Figma source | Code source | Weight | |---|---|---|---| | Components used | instances in the frame | imports / rendered components | 25% | | Variants & props | instance properties | props passed | 20% | | Tokens (color, space, radius, type) | get_variable_defs | classes / computed styles | 30% | | Layout & spacing | auto-layout gaps/padding | computed box model | 15% | | Visual diff | get_screenshot | Playwright screenshot | 10% |

Before you start

  • ☐ The built UI is running: pnpm dev (Storybook) or pnpm playground
  • ☐ For a story, copy its iframe URL: open the story → "Open canvas in new tab" (iframe.html?id=…)
  • ☐ Playwright browser installed once: npx playwright install chromium

Steps (what the skill does)

  1. Figma side: reads the frame with the Figma MCP (instances, variant properties, bound variables, auto-layout, screenshot) and flags detached/unbound layers.
  2. Built side: runs pnpm qa:snapshot <url> --name <x> --theme both. It saves screenshots and, for every element, the DS component it belongs to (data-ds) and its computed styles translated back to token names, plus any hand-rolled controls and raw values.
  3. Compares and scores with the weights above; the final score is the lowest theme score.
  4. Writes qa-output/<name>/report.md: score, mismatch table (element · Figma · built · fix in Code / Figma / DS), design-side issues, screenshots.

Sample prompt (Claude Code, in the repo)

Use ds-design-qa.
Figma frame: <URL with node-id>
Built UI: http://localhost:6006/iframe.html?id=pages-fintech-app--dashboard-page
Viewport 1280x800, both themes. Name: dashboard.
Report only, don't fix anything.

Follow-up prompt

Fix the "Code" mismatches from qa-output/dashboard/report.md, rerun ds-design-qa and show the new score.
List the "Figma" ones so I can fix them in the design.

Output: score + mismatch table + screenshots → issues or a fix PR Done when: ☐ score ≥ 90 ☐ every mismatch is either fixed or accepted with a reason

Chapter 7

Handoff & build

Getting features from Figma into the product using the system.

Recipe G

Hand off a feature to engineering

Goal
Engineers (and their agents) can build the feature using only the DS, with no guessing
Who
Product designer → Frontend engineer
Where
Cowork (spec) → GitHub issue in the product repo
Attach / provide
Figma flow URL (all screens + states) · PRD/ticket · edge cases you know
Skills
✅ ds-handoff (builds on 🧩 design:design-handoff) · 🧩 design:ux-copy (optional)
Connectors
Figma · GitHub (or Jira/Linear if that's where tickets live)

Steps

  1. Make sure every element in the Figma flow is a DS instance (no detached layers).
  2. Claude writes the handoff spec in DS language: per screen, which components, which props, which DESIGN.md pattern applies.
  3. Claude flags DS-GAPs, i.e. things the system doesn't cover → "New component" issues in the DS repo (→ Recipe C).
  4. Post the spec on the product ticket. Engineers build with Recipe H.

Sample prompt (Cowork with the repo folder connected, or Claude Code)

Use ds-handoff for the KYC flow.
Figma flow: <URL of the page/section with all screens>
PRD: attached (or <link>)
Breakpoints: 375 / 1280. Save the spec as handoff/kyc.md.
If you find detached layers, stop and list them first.

Commands

Command Does
pnpm dev Builds tokens and opens Storybook (localhost:6006)
pnpm playground Simulated product (localhost:5173)
pnpm tokens Rebuilds CSS variables from token JSON
pnpm check Typecheck + raw-value audit (the same as CI)
pnpm --filter @tawan-design/ui catalog Regenerates catalog.json
pnpm changeset Describe your change (patch/minor/major)
npx figma connect publish Publishes Code Connect snippets to Figma Dev Mode
pnpm qa:snapshot <url> --name x --theme both Built-UI side of design QA (screenshots + tokens per element)
pnpm catalog:summary Code side of a drift check (components, props, stories, Code Connect)

Semver in one line

patch = fix · minor = new component/variant/token · major = rename or removal (needs a migration note)

Golden rules

  1. Figma variables are the source of token values. Never hand-edit token JSON.
  2. A pattern becomes a component only after it works in ≥2 real screens.
  3. Figma property names = code prop names.
  4. Nothing reaches main without a PR and design approval.
  5. When an agent gets it wrong, fix the docs (one specific sentence), not just the code.
  6. Keep AGENTS.md an index. If you're typing values into it, they belong somewhere else.
